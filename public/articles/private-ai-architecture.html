The Private AI Box I Would Actually Put in Front of a Customer

A 7-minute field guide to local models, typed outputs, vector search and guardrails that survive the move from demo to deployment

By Ankit Samriwal · September 2026

A 7-minute field guide to local models, typed outputs, vector search and guardrails that survive the move from demo to deployment

Most AI architecture diagrams begin with the model.

That is usually the wrong place to begin.

The model is only one component in a working system. The harder questions sit around it: Who can reach the service? Where does customer data go? Which decisions may the model influence? What happens when its output is malformed? Can we trace the answer back to evidence? Can we restore the system after a failure?

I wanted a reference architecture that answers those questions without requiring an enterprise cloud bill on day one.

The result is a simple pattern: a controlled edge, one private compute plane, a local small language model, deterministic rules, typed outputs, retrieval, observability and a tested recovery path.

Start with the boundary, not the model

Users may arrive through a messaging channel, a web interface, a mobile app or an operator console. Those channels should not connect directly to the model or the database.

They first meet an experience layer, then a controlled edge. The edge handles DNS, authentication, access policy, rate limits, bot controls and routing. A secure tunnel is the only application path into the private compute plane.

That gives the design its first useful property: the application server does not need open public ports for its database, vector store, model server or integration tools.

The private box remains private.

This is a stronger starting point than deploying five public services and trying to add security after the demo works.

One private compute plane

The central unit is a Linux virtual server running isolated containers. It contains five distinct responsibilities:

  • an API gateway for authentication and routing
  • an integration layer built around typed tools
  • a deterministic rules engine
  • a local quantised small language model
  • a data plane with relational and semantic storage.

The separation matters. A model should not have direct write access to transactional data. An integration tool should not receive a blanket filesystem permission. A frontend should not know a database credential. Each component gets its own identity and the smallest useful set of permissions.

For an early build, this can run on one server. That is an economic choice, not an excuse to collapse the boundaries. Separate containers, networks, credentials, logs and release versions still matter.

Rules decide what is non-negotiable

The most important line in the diagram is not a network arrow. It is the line between the rules engine and the model.

Hard requirements belong in deterministic code.

If a policy says an input is ineligible, a model cannot talk its way around it. If a compliance check must always run, it should not depend on a probabilistic answer. If a threshold is fixed, it remains a threshold.

The small model is useful for bounded judgement:

  • classification
  • extraction
  • ranking
  • summarisation
  • matching a question to the right evidence
  • proposing a next step.

This hybrid design is less theatrical than asking one large model to do everything. It is also easier to test, explain and trust.

Typed output is the contract

A model response is untrusted input.

Before an application uses it, the response should cross a typed boundary. The schema defines required fields, allowed values, ranges, citations, error states and the actions the receiving application may take.

A valid result might contain:

  • the task category
  • the recommended decision class
  • the evidence identifiers used
  • a confidence value
  • a reason code
  • an explicit next action.

Malformed output does not flow downstream. It is rejected. A recoverable formatting error may be retried within a limit. An unsupported or low-confidence case should abstain or move to human review.

This sounds like ordinary software engineering because it is. AI does not remove the need for contracts between services. It increases it.

Retrieval needs receipts

A vector database makes local knowledge searchable. It does not make the result true.

The data layer therefore keeps two different jobs visible:

  • a relational store for users, events, decisions, metadata and smaller vector indexes
  • a dedicated vector store for larger semantic collections and filtered retrieval.

Every retrieved item should preserve its source ID, chunk ID and relevant metadata. Tenant or application filters must be applied to every query, not added as a user-interface convention.

Important answers should carry evidence. Retrieved text must also be treated as untrusted content. A document can supply facts. It cannot rewrite system policy, grant a tool permission or instruct the platform to ignore its rules.

The point of retrieval is not merely to make the answer sound informed. It is to make the answer inspectable.

The integration layer is a control point

A common tool protocol can make applications easier to connect. It can also turn one weak permission into a large attack surface.

The integration gateway should therefore enforce four things:

  1. Only approved servers and tools are available.
  2. Every tool has a typed argument schema.
  3. Execution time, output size and retries are capped.
  4. The audit event records the caller, tool, purpose and result status.

Arbitrary shell access and unrestricted filesystem access do not belong in the default toolset. Credentials are scoped per service. A tool request inherits the identity and policy context of the original call.

Integration speed is useful only when authority remains clear.

Observability must include model quality

Traditional service metrics are still necessary:

  • request volume and success rate
  • p50 and p95 latency
  • CPU, memory, disk and I/O
  • container restarts
  • database connections
  • queue depth
  • backup age.

An AI service needs another set:

  • model, prompt and schema version
  • schema rejection rate
  • abstention rate
  • retrieval quality
  • rule/model disagreement
  • evaluation-set result
  • operator override rate.

Logs should use request IDs and redacted fields. Raw confidential prompts and documents should not become a second uncontrolled data store inside the logging system.

The target is not to record everything. It is to preserve enough evidence to explain failure and manage change.

Security is a rail across every layer

Security is not a box at the bottom of the architecture. It runs down the side because it applies everywhere.

The minimum useful baseline is straightforward:

  • multi-factor authentication for operators
  • separate service identities
  • default-deny firewall rules
  • no public database, model or tool ports
  • secrets outside source control
  • encrypted backups
  • tenant-aware data access
  • pinned container images and dependency scans
  • a software bill of materials
  • a documented rollback path
  • adversarial tests for prompt injection and tool misuse.

The model-specific guardrail is equally simple: rules remain authoritative, typed validation is mandatory, evidence is attached where it matters, and uncertainty has an abstention path.

Free tier first, but not free of discipline

The early economics are attractive.

A static frontend, secure tunnel, access controls and modest object storage can begin on free allowances, subject to each provider's current terms. The databases, integration gateway and local inference software can be self-hosted without licence cost.

The paid component is usually the server.

As a planning range in September 2026, a light prototype class begins around $6.49 a month. An 8 GB class is around $9.99, and a 16 GB class around $18.49, before VAT, IPv4 and support. These are reference prices, not a production sizing promise.

The correct progression is:

  • use free edge and storage allowances while demand is unproven
  • use a light server for synthetic or low-volume work
  • move to 8 GB for one vector or model workload
  • use 16 GB when several applications share the database, vector store and inference service
  • consider managed services when recurring revenue or operational risk justifies them.

Free tier first does not mean production claims on prototype infrastructure. Reliability, recovery, support and provider limits still need an owner.

The deployment gate

Before external users arrive, I would require evidence for ten questions:

  1. Is the data boundary approved?
  2. Does an external scan show no public database, model or tool port?
  3. Does every identity have an owner and revocation path?
  4. Have cross-tenant access and tool abuse been tested?
  5. Do deterministic rules win every designed conflict?
  6. Can invalid model output reach an action? The answer must be no.
  7. Does the locked evaluation set pass for the exact deployed version?
  8. Has an encrypted backup been restored into a clean environment?
  9. Do alerts reach a named operator?
  10. Has rollback been exercised rather than described?

A demo proves that a path can work. This gate begins to prove that the system can fail safely.

What this architecture is really for

The attraction of a local small model is not that it replaces every large model.

It gives the system a cheap, fast and private judgement layer for narrow work. Deterministic rules handle what must not vary. Retrieval supplies evidence. Typed output makes the response usable. Human review remains available where consequence or uncertainty demands it.

That combination is more useful than a bigger model inside a weaker system.

The one-line design principle is this:

Keep the box private, keep the data local, keep rules authoritative, and validate every model output before use.
